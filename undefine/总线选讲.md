# H0. 最简单的总线

```Plain Text
『 IFU 』--inst--->『 IDU 』
```

在单周期处理器中：
+ 主动发起通信的模块叫master(主设备)；
+ 响应通信的模块叫slave(从设备)；

单周期处理器定义该通信协议，如下：
+ master(IFU)往slave(IDU)发送消息(当前指令inst)；
+ 双方约定，只要master发送，slave理解收到；
+ 上述行为每周期都发生；

---

```Plain Text
『 IFU 』--inst+valid--->『 IDU 』
```

在更真实的处理器中：
+ IFU并非每周期都能取到指令；
+ IDU需要等待IFU完成取值后，才能进行译码；

通信协议，如下：
+ master(IFU)往slave(IDU)发送消息(当前指令inst)；
+ 双方约定，只要master发送，slave理解收到；
+ 上述行为仅在**valid**有效时发生；

---

```Plain Text
+-----+  ---inst+alid--->  +-----+
| IFU |                    | IDU |
+-----+  <-----ready-----  +-----+
```

在更真实的处理器中：
+ IFU并非每周期都能取到指令；
+ IDU需要等待IFU完成取值后，才能进行译码；
+ IFU需要等待IDU完成译码后，才能发送下一条指令；

通信协议，如下：
+ master(IFU)往slave(IDU)发送消息(当前指令inst)；
+ 双方约定，若master发送，且**ready**有效时，slave理解收到；
+ 上述行为仅在**valid**有效时发生；

>+ 这就是**异步总线**，在`valid & ready`时才发生，称“**握手**”；
>+ `valid & ！ready`时，master需要暂存消息，避免丢失；
>+ **使用valid和ready可以实现多级流水。**

# H1. 异步总线

**异步总线的RTL实现——接口信号**

Chisel提供了`Decoupled`模板，通过元编程轻松实现异步总线接口，`Decoupled`模板自带valid和ready：
```scala
class Message extends Bundle{
	val inst = Output(UInt(32.W))
}

class IFU extends Module{
	val io = IO(new Bundle{val out = Decoupled(new Message)})
}

class IDU extends Module{
	val io = IO(new Bundle{val out = Filpped(Decoupled(new Message))})
}
```

---

**异步总线的RTL实现——模块逻辑**

master和slave需要根据握手信号的情况来实现约定的总线协议
+ 不同情况做不同的事情(通信协议) -> 状态机
+ 总线的RTL实现=接口信号+状态机


master的状态转移图：
![[Pasted image 20261113203628.png|504]]
```scala
class IFU extends Module{
	val io = IO(new Bundle{val out = Decoupled(new Message)})
	
	val s_idle :: s_wait_ready :: Nil = Enum(2)
	val state = RegInit(s_idle)
	state := MuxLookup(state, s_idle, List(
		s_idle -> Mux(io.out.valid, s_wait_ready, s_idle),
		s_wait_ready -> Mux(io.out.ready, s_idle, s_wait_ready)
	))
	io.out.inst := //有指令需要发送
	// ...
}
```

# H2. 系统总线

**系统总线=连接处理器和存储器以及设备之间的总线(SoC片内，PCIe是SoC片外)。**

1. 如果**处理器同时读写同一个地址**，该行为需要RTFM(有和能undefined)，大部分的SRAM和FPGA中的Block RAM都有定义该行为。
2. 由于电气特性，例如**电容的充放电、充电刷新较慢且不固定**，通常**存储设备的==读延迟==要大于CPU的1周期**，也就是CPU请求速度>服务速度，导致整个系统效率很低，也就是Memory Wall。
3. 为解决请求和服务速度不同，需要**异步总线**，添加握手信号。

**异步系统总线：**

```Plain Text
+-----+                             +-----+
|     | ---araddr[log2(N)-1:0]--->  |     |
|     | ---------arvalid--------->  |     |
|     | <--------arready----------  |     |
|     | <------rdata[31:0]--------  |     |
|     | <--------rvalid-----------  |     |
| CPU | ---------rready---------->  | MEM |
|     |                             |     |
|     | ---waddr[log2(N)-1:0]---->  |     |
|     | -------wdata[31:0]------->  |     |
|     | ----------wen------------>  |     |
|     | -------wmask[3:0]-------->  |     |
|     | -------wvalid------------>  |     |
|     | <------wready-------------  |     |
+-----+                             +-----+
```

在一次读数据的过程中，master和slave都需要等待两次握手：
+ master先等arready，确保slave接收读地址后，再等rvalid接受读数据；
+ slave先等arvalid接收读地址，再等rready，确保master接收读数据；


>**握手信号可以屏蔽通信双方的处理延迟。**

# H3. 错误处理


读写请求可能会出错，例如超出存储区域的边界。

```Plain Text
+-----+                             +-----+
|     | ---araddr[log2(N)-1:0]--->  |     |
|     | ---------arvalid--------->  |     |
|     | <--------arready----------  |     |
|     | <------rdata[31:0]--------  |     |
|     | <------rresp[1:0]---------  |     |
|     | <--------rvalid-----------  |     |
| CPU | ---------rready---------->  | MEM |
|     |                             |     |
|     | ---waddr[log2(N)-1:0]---->  |     |
|     | -------wdata[31:0]------->  |     |
|     | ----------wen------------>  |     |
|     | -------wmask[3:0]-------->  |     |
|     | -------wvalid------------>  |     |
|     | <------wready-------------  |     |
|     | <------bresp[1:0]---------  |     |
|     | <------bvalid-------------  |     |
|     | -------bready------------>  |     |
+-----+                             +-----+
```

通过rresp和bresp(b表示backward)向master回复读写操作是否成功：
+ 若失败，CPU可抛出异常，通知软件处理。RISC-V中可抛出3种Access Fault异常；
+ 为了让master成功收到写回复信号，也需要握手；



>综合H2和H3的部分，我们就基本上了解了**AXI-Lite协议**的核心机制：
>1. 将写地址和写数据分开，写地址通过单独握手；
>2. 分组，并将wmask改名为wstrb；

# H4. 实际使用中的若干问题*

1. 要使用系统总线，需要将处理器从单周期升级为**多周期**，处理器的访存延迟至少是1周期，不满足单周期处理器的特征；

2. **避免两种情况**：
   + **死锁(deadlock)**：master和slave都在等待对方先将握手信号置1。
     + master等slave将ready置1后，再将valid置1；
     + slave等master将valid置1后，再将ready置1；
   + **活锁(livelock)**：局部看没有卡死，全局看没有进展。
     + master和slave都在试探性地握手，但试探失败后又都取消握手；
     + ![[Pasted image 20261114175903.png|525]]

>解决办法：对握手信号的行为添加额外的约束，具体RTFM。


3. **总线的仲裁**
   + CPU中IFU需要从内从取指，LSU需要读写内存中的数据，这里的"内存"是物理上同一个存储器。**多个master访问同一个slave**。
   + 需要一个 **仲裁器(Arbiter)** 来决定当前谁可以访问
	   + 获得访问权的master将得到放行，可以成功访问slave；
	   + 其他master的请求将阻塞，等待获得访问权限的master访问结束后，参与下一轮仲裁；
	   + 仲裁器的实现=状态机![[Pasted image 20261114180400.png|624]]


==🔴仲裁器：==
+ **调度**：选择一个正在发送有效请求的master；
+ 阻塞：阻塞其他master的访问；
+ 转发：将获得访问权的master的请求转发给slave，并在slave的请求到达时，将其转发给之前的master；

在复杂系统中，调度策略还需要考虑：
+ 避免饥饿：任一个master都能在有限次仲裁后获得访问权；
+ 避免死锁：造成的阻塞不应使整个系统出现循环等待的现象；


4. **支持多个设备：**
	真实的计算机系统中不仅仅只有存储器，还有其它设备：
	+ 内从映射I/O [[处理器芯片设计全流程#H5. 程序和输入输出]]，通过不同的内存地址来指示不同的设备；
	+ 在仿真环境中，通过`pmem_read()`和`pmem_write()`实现 [[处理器芯片设计全流程#H3. 逻辑设计]]；
	+ 在真实环境中，通过 ==🔴**crossbar(有时也写作Xbar)**== 实现；![[Pasted image 20261114181418.png]]
		+ Xbar根据请求地址将请求转发给不同的下游(设备或另一个Xbar)；
		+ Xbar发现目标地址无设备时，resp信号返回decerrr错误(地址译码错误)；
		+ 地址译码=将请求地址转换为下游编号，是Xbar的核心功能；




>**Arbiter和Xbar可合并成多进多出的Xbar(也称Interconnect，总线桥等)**。



多个设备带来的问题：
![[Pasted image 20261114182228.png|561]]

RISC-V的内存访问检查机制：
1. 为每段地址空间添加若干**权限属性(RWX等)**；
2. 在IFU发出取指请求前，**先检查请求的地址所属的地址空间是否可执行**，否则，则抛出Access Fault异常；
3. RISC-V提供两种**物理内存检查机制**：
	+ PMA(Physical Memory Attribute)：地址空间在系统中固定，通过RTL实现权限表，在RTL设计时写入；
	+ PMP(Physical Memory Protection)：地址空间动态分配(如PCI-e等)，通过CSR实现权限表，在系统初始化时由软件写入；
4. 如果**支持虚拟内存**，则能实现更细粒度的权限检查功能；

如果上述都不支持，开发裸机程序的时候就要特别小心，如果程序飞了，后果很难想象！
